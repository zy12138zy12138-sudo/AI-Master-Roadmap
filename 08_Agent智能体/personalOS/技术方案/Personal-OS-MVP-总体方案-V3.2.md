## 二、产品定位

Personal OS 是一款个人自用的 iPhone 执行管理 App，核心目标是把长期目标转化为可执行计划，通过任务、复盘和反馈形成闭环，重点解决：

- 规划投入过多、开始执行较慢；
- 任务过大导致拖延；
- 手机、情绪和精力波动影响执行；
- 完成结果缺少连续记录与反馈；
- 多个长期项目之间缺少统一优先级。

产品成功标准不是功能数量，而是用户能持续完成：

```text
目标 → 计划 → 今日任务 → 执行 → 复盘 → 调整
```

## 三、用户与使用边界

- 单人自用，不商用；
- 在 iPhone 的 Expo Go 中运行；
- 任务、计划和复盘数据本地优先；AI 请求通过最小化服务端代理完成；
- 不发布 App Store；
- 不建立账号、登录、支付或云同步；
- 使用当前固定界面主题，不提供深色/浅色模式切换，后续版本也不规划该功能；
- 不保存 DeepSeek 账号、密码；DeepSeek API Key 不进入 App、不提交 Git；
- App 不显示 ChatGPT 名称或入口；
- Day 8 起接入 DeepSeek API，不接 OpenAI API；
- AI 建议必须先展示给用户确认，不允许静默修改或删除数据。

## 五、任务优先级 V1.0

| 级别 | 定义 | 使用约束 |
|---|---|---|
| P0 | 紧急且重要，今天必须完成 | 每天建议 1—2 项，不强制限制 |
| P1 | 重要任务，今天优先完成 | 优先安排在高精力时段 |
| P2 | 常规任务，按计划推进 | 新任务默认值 |
| P3 | 低优先级，有余力再完成 | 可延期或删除 |

展示与排序规则：

1. 任务优先按 `P0 → P1 → P2 → P3` 展示；
2. 同一优先级内保持 `sort_order ASC`；
3. 已完成状态不改变任务优先级；
4. 默认优先级为 P2，避免普通任务被误标为重要任务；
5. P0 数量限制先通过产品提示实现，不在 MVP 阶段做强制拦截。

## 八、数据库正式基线 V3

```text
数据库：personal-os.db
当前已验收版本：3
数据表：projects、tasks
日期：本地时区 YYYY-MM-DD
今日查询：project_id + scheduled_date
排序字段：sort_order
复合索引：project_id、scheduled_date、sort_order
任务 ID：SQLite randomblob(16)
```

Day 3 今日任务查询：

```sql
WHERE project_id = ?
  AND scheduled_date = ?
ORDER BY sort_order ASC
```

Day 3 数据库曾包含以下旧约束：

```sql
CHECK (priority IN ('P0', 'P1'))
```

Day 4 已通过事务内安全重建 `tasks` 表完成 V2→V3 迁移，并将约束扩展为 P0/P1/P2/P3。最终结果：

- 保留全部任务的 ID、项目、标题、优先级、完成状态、日期、排序和时间字段；
- 重建既有索引；
- 支持新数据库按 `0 → 1 → 2 → 3` 建立，现有真机数据库按 `2 → 3` 升级；
- `PRAGMA user_version = 3`；
- 迁移失败会回滚，不留下半完成结构。

当前任务查询排序为：

```sql
WHERE project_id = ?
  AND scheduled_date = ?
ORDER BY CASE priority
  WHEN 'P0' THEN 0
  WHEN 'P1' THEN 1
  WHEN 'P2' THEN 2
  WHEN 'P3' THEN 3
  ELSE 4
END,
sort_order ASC
```

后续表：

- `daily_reviews`：每日复盘主体；
- `review_metrics`：如确需结构化指标再增加；
- `ai_decisions`：AI 请求摘要、结构化结果、状态与生成时间；
- `ai_decision_actions`：建议动作、目标任务、确认状态与实际应用结果；
- Day 5 明确复用 `tasks.scheduled_date`，不创建独立 `plans` 表。

## 九、技术架构

统一技术基线：

```text
Windows
+ VS Code
+ Codex
+ Expo SDK 54
+ React Native
+ TypeScript
+ Expo Router
+ expo-sqlite 16.0.10
+ iPhone Expo Go
+ 本地 SQLite
+ 安全服务端代理
+ DeepSeek API
```

明确排除：

- SwiftUI、Xcode、Mac 专属开发链；
- 账号系统与业务数据云同步；
- OpenAI API；
- 将 DeepSeek API Key 写入 App、源码或 Git；
- 新 ORM、全局状态框架或不必要 UI 框架；
- 为单一小功能升级 Expo SDK。

工程原则：

- 数据访问集中在数据库模块；
- SQL 使用参数绑定；
- 迁移顺序执行并由 `PRAGMA user_version` 管理；
- 日期统一复用本地日期工具；
- 页面不维护第二份固定任务数据源；
- 每次开发限定文件范围并选择性 Git 暂存。
- AI 请求只发送完成决策所需的最少数据；
- 服务端负责密钥、超时、限流、错误处理与输出校验；
- AI 结果必须通过结构化 Schema 校验后才能进入确认流程。

## 十、DeepSeek API 协作方案

产品内统一使用“AI 决策助手”，底层模型为 DeepSeek，不显示 ChatGPT。

```text
App 汇总最小必要的任务/计划/复盘数据
→ 安全服务端代理调用 DeepSeek API
→ 返回经过 Schema 校验的结构化决策
→ App 展示建议和修改前后对比
→ 用户接受、修改或拒绝
→ 仅将已确认动作写入本地 SQLite
```

技术边界：

- DeepSeek API Key 仅保存在安全服务端环境变量；
- App 不直接持有密钥，不在日志中记录密钥或完整敏感请求；
- 请求失败、超时或结构不合法时，不修改任何本地任务；
- 分析和排序可直接展示；新增、拆分、延期、改优先级须用户确认；
- 删除任务和改变长期目标必须单独明确确认；
- 不保存 DeepSeek 账号密码，不实现无确认自动执行。

## 十一、AI 决策与反馈模型定位

### 11.1 决策引擎

AI 决策引擎通过 DeepSeek API 读取结构化上下文。输入至少包含：

- 当前长期目标与项目；
- 当日可用时间和精力；
- 待办任务、日期和优先级；
- 最近未完成原因；
- 当日特殊限制。

输出为固定 JSON：决策摘要、今日核心任务、推荐顺序、优先级调整、拆分/延期建议、理由、风险和第一步行动。

### 11.2 目标权重模型

保留“收益、紧急性、长期价值、成本、风险”等维度作为人工决策参考，MVP 不开发自动评分算法。

### 11.3 执行评分模型

复盘页具备真实数据后再计算，建议最低维度：

- 完成率；
- P0 完成情况；
- 开始执行及时性；
- 计划合理性；
- 主观精力和阻碍。

评分用于识别执行问题，不用于惩罚或单纯追求高分。

### 11.4 反馈学习引擎

DeepSeek 基于近期复盘识别重复阻碍并输出一条可验证的调整策略。App 不训练模型，但可保存必要的决策、确认与执行结果，用于后续反馈分析。

## 十二、Prompt 系统 V2.0

API 请求由 system instruction、用户上下文和 JSON Schema 组成。核心要求为：

```text
【角色】
你是 Personal OS 的个人执行决策引擎。基于目标、时间、精力、任务和复盘生成克制、可解释、可执行的建议。

【日期与可用时间】
...

【当前项目与目标】
...

【任务列表】
- [P0/P1/P2/P3] 任务｜日期｜完成状态

【近期复盘】
...

【已知阻碍】
任务过大 / 手机分心 / 情绪 / 精力不足 / 其他

【决策约束】
1. 控制当日任务量，不把所有任务都标为高优先级；
2. 每项建议必须给出理由和第一步；
3. 区分建议、需确认修改和高风险修改；
4. 不得虚构任务、时间、健康状态或完成记录；
5. 只返回符合约定 Schema 的 JSON。
```

完整字段、示例和错误恢复策略由《Personal OS AI 决策与 Prompt 系统 V2.0》维护。
